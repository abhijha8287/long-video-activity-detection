# Design: Activity Detection & Classification in Long Videos — Baseline System

Generated by /office-hours on 2026-09-09
Repo: Cerebralzip2 (local, not yet a git repo)
Status: APPROVED

## Problem Statement

Build a system that takes a long, untrimmed video and outputs temporal segments
`{start, end, label, confidence}` for 10 activity classes (Fire/Smoke, Fighting/Assault,
Falling, Intrusion/Trespassing, Loitering, Vandalism, Theft/Chain Snatching, Crowd
Formation, Running-in-restricted-zone, Abandoned Object), evaluated against ground
truth with temporal-IoU-based detection metrics, and runnable via
`python inference.py --video <new_video.mp4>` on video never seen during development.
This is a technical take-home assignment (job-interview evaluation), not a product —
the evaluator explicitly values an honest, runnable baseline over an ambitious system
that can't be justified.

## Premises (confirmed with user)

1. No real dataset exists in this environment. Any video(s) used for quantitative
   evaluation must be sourced (public-domain/CC-licensed clips) or self-constructed,
   and the report states this plainly rather than implying a provided dataset.
2. No GPU + no training data → transfer learning from pretrained encoders (zero-shot
   or lightweight few-shot head), not training a video model from scratch.
3. **A single whole-clip video-encoder classifier is a poor fit for 6 of the 10
   classes** — Loitering, Intrusion, Crowd Formation, Running-in-a-zone, Abandoned
   Object, and Falling are defined by position/geometry over time relative to a scene
   (dwell time in a zone, object–owner separation, local density, sudden bbox aspect
   change), not by appearance a Kinetics-pretrained action classifier has ever seen
   labeled data for. Confirmed: build a hybrid system — detection + tracking + a rule
   engine for these, a pretrained appearance model over sliding windows for the rest
   (Fire/Smoke, Fighting/Assault, Vandalism, Theft).
4. Nothing gets tuned to one demo video. Thresholds/window sizes are chosen via a
   validation split or first-principles reasoning, documented as such, and never
   tuned against whatever video is used for final reporting.

## Approaches Considered

The geometry branch (detection + tracking + rule engine, for the 6 position/dwell-
defined classes) and the overall hybrid split were settled by Premise 3, not
re-litigated here. What these three approaches actually compare is the **appearance
branch** backbone (the 4 classes that need a genuine visual/semantic judgment: Fire/
Smoke, Fighting/Assault, Vandalism, Theft).

### Approach A: CLIP zero-shot appearance branch (chosen)
Geometry branch: YOLO11n detector + ByteTrack tracker feeds the rule engine
(dwell time, zone occupancy, local density, bbox-shape change, object–owner
separation). Appearance branch: CLIP (ViT-B/32) zero-shot image–text similarity
over sliding-window sampled frames for the 4 appearance classes. Effort M, Risk Low —
no training data required for anything, runs on CPU, every class traces to a
concrete, explainable mechanism. Weakness: CLIP sees single frames, not motion, so
temporally-defined appearance actions (a punch landing) rely on frame-level
appearance cues rather than true motion modeling — see Feasibility Risks below for
which specific classes this weakness likely hurts most.

**Explicitly out of scope for this build:** a few-shot linear probe head on top of
CLIP embeddings, auto-activating once labeled clips exist for a class. This is a
natural extension the code should not actively block, but it is not part of the
initial implementation, has no step in the Next Steps below, and should not be
described as a built feature until it has one.

### Approach B: Shared pretrained video encoder (X3D-S) for appearance classes
Same geometry branch; swaps CLIP for a true video-native encoder run per sliding
window. Rejected: no CUDA means X3D forward passes are markedly slower per window on
this machine, and Kinetics-400's label space doesn't map cleanly to any of our 10
classes, so zero-shot text-side matching is weaker than CLIP's native image-text
alignment — heavier dependency chain for uncertain gains on only 4/10 classes.

### Approach C: VLM frame-captioning + keyword/embedding match
Same geometry branch; a small multimodal captioner describes each window, matched
against class descriptions. Rejected: heaviest compute per window on CPU/MPS, most
failure surface to defend live in an interview, no clear accuracy edge over A given
there's no real labeled data to validate calibration either way.

## Recommended Approach

**Approach A.** Best fit for the actual constraint set: zero GPU, zero provided data,
must be explainable component-by-component in an interview, and evaluation honesty
matters more than a few points of accuracy on classes that can't be properly measured
without real footage anyway.

### Pipeline

```
Long video (+ optional zone config for this camera/site)
  → frame sampling (shared decode pass, ~5 fps for detection; native stride for CLIP windows)
  → GEOMETRY BRANCH: YOLO11n detection → ByteTrack tracker → rule engine
       (dwell time, zone occupancy, density, bbox-shape, owner-separation)
       → per-frame class scores in [0,1] for 6 classes (per-rule normalization, see below)
  → APPEARANCE BRANCH: sliding windows → CLIP zero-shot (image ↔ class prompts)
       → per-window softmax-normalized class scores in [0,1] for 4 classes
  → place both branches' scores on one shared timeline (class-disjoint: no class is
       scored by both branches, so this is placement, not score fusion — see below)
  → confidence thresholding, per class (validation-selected, not test-tuned)
  → temporal smoothing (median/majority filter over adjacent windows/frames)
  → consecutive-window grouping + segment merging (+ optional temporal NMS)
  → final segments {start, end, label, confidence} — segments from different
       classes may overlap in time (e.g. Crowd Formation concurrent with Running);
       segments of the *same* class never overlap after merging
```

**Runtime budget:** target ≤2× video real-time end-to-end on this hardware (CPU/MPS,
M5, 16GB). Achieved by detection at a reduced sampling rate (~5 fps, not native fps)
with track interpolation between sampled frames, and CLIP windows evaluated once per
stride rather than per frame. If a video blows this budget in practice, that's
reported as a measured number in the report, not silently dropped.

### Score normalization (resolves branch "merge" ambiguity)

The two branches never score the same class, so there is no cross-branch score
fusion to calibrate. Each branch independently normalizes its own outputs to [0,1]:
CLIP scores are softmax over that window's class-prompt similarities (already
comparable across classes within the appearance branch). Rule-engine scores are
produced per rule via an explicit, named function (e.g. dwell-time score =
`sigmoid((dwell_seconds - threshold) / scale)`, density score = normalized count
above a per-zone density threshold) — each rule's scale/threshold constants live in
`configs/classes.yaml`, not hardcoded, per the assignment's own "configuration over
constants" rule. "Merging on one timeline" means placing these two independently-
normalized, class-disjoint streams into one data structure for the shared
thresholding/smoothing/segment-building steps that follow — not blending them.

### Zone specification (resolves a real conflict with the success criteria)

Intrusion/Trespassing and Running-in-a-restricted-zone are *defined* relative to a
restricted region that cannot be inferred from pixels alone — "restricted" is a
site policy, not a visual property. As originally drafted this conflicted with
"runs on any new video with no code changes." Resolution: `inference.py` takes an
**optional** `--zones <name>` argument pointing at a small YAML file (pixel polygons
for restricted/no-loitering/etc. regions, defined once per camera/site and reused
across every video from that camera — not per video). This does not violate "no
code changes for a new video": a new video from an already-configured camera needs
no new zone file; a genuinely new camera angle needs a one-time few-line YAML polygon,
which is a data/config change, not a code change — same category as needing a new
class prompt for a genuinely new class.

**Explicit fallback when `--zones` is omitted:** Intrusion and Running-in-zone are
reported as **not evaluated / not applicable** for that run rather than guessed at
(e.g. via a naive frame-border heuristic that would produce misleading detections).
This is stated in the CLI's printed summary and in the README, not silently
swallowed. The other 8 classes are unaffected and run zone-config-free.

### CLIP prompt strategy

Each appearance class gets 3-5 short text prompt variants (paraphrases, e.g. for
Fire/Smoke: "a photo of fire and smoke", "flames burning indoors", "smoke filling a
room") defined in `configs/classes.yaml` — editable without touching code, per the
assignment's configuration requirement. Per window, CLIP image-embedding similarity
is computed against every prompt for every class; a class's window score is the max
similarity across its own paraphrases, then softmax-normalized across classes. This
gives prompt engineering a config-only iteration loop during the experiment phase.

### Rule-to-class mapping (each of the 6 geometry classes gets its own primary trigger)

Six rules, one primary trigger per class, so no two classes share a mechanism:

| Class | Primary rule |
|---|---|
| Intrusion/Trespassing | zone-occupancy — any person track present inside a restricted zone at all, near-immediate trigger |
| Loitering | dwell-time — person track present inside a (loitering) zone for ≥ T_dwell |
| Running-in-restricted-zone | velocity — person track inside a zone AND estimated speed (bbox-centroid displacement/sec, normalized by bbox height to stay roughly scale-invariant to camera distance) exceeds a velocity threshold, sustained ≥ T_min to reject single-frame tracker noise |
| Crowd Formation | density — ≥ N person tracks within radius R of each other for ≥ T_density |
| Falling | bbox-shape change — sudden bbox aspect-ratio flip (tall→wide) followed by minimal subsequent movement |
| Abandoned Object | stationary-object + owner-separation (see below) |

Running and Intrusion share the same zone-config mechanism but different trigger
conditions (presence vs. sustained speed), so they're distinguishable in practice,
not just in name.

### Abandoned Object logic

An object (from a fixed set of YOLO classes: backpack, suitcase, handbag, etc.)
becomes an "abandoned object" candidate when: (a) its track is stationary (centroid
movement below a pixel threshold) for ≥ T_static seconds, AND (b) no person track
has been within a proximity radius of it for ≥ T_separation seconds. "Owner" is
defined as the person track that was nearest to the object in the frames just
before it became stationary; separation duration is measured from the last frame
that person track was within the proximity radius. Both thresholds live in
`configs/classes.yaml`.

### Data sourcing plan (executed during implementation, not during this session)

Since no dataset exists, evaluation needs at least 2–3 videos with real ground
truth. Plan: assemble long test videos by concatenating a handful of short,
public-domain / CC-licensed clips (with `ffmpeg`) into synthetic-but-real-footage
long videos, hand-authoring the ground-truth JSON since the concatenation points
and source clips are known exactly. This is stated explicitly in the report as
self-constructed evaluation data, not a claim of a provided dataset. Classes for
which no legally obtainable footage can be found in the time available (this is
expected for some appearance classes, e.g. real chain-snatching or arson footage)
get documented as **not quantitatively evaluated**, with a qualitative CLIP-prompt
calibration check instead — never a fabricated number.

### Temporal windowing

No activity-duration distribution exists yet to derive window/stride from (no
dataset). Starting point for the appearance branch: 3s window / 1.5s stride
(50% overlap) — short enough to catch brief bursts (a shove, a grab) without
producing so many overlapping windows that merging becomes noisy. This is a
documented starting hypothesis, tuned via the window/stride/threshold experiments
in the implementation's evaluation phase against a held-out portion of whatever
evaluation video(s) get constructed — never tuned against the final report numbers.
The geometry branch runs on every tracked frame (no windowing needed — dwell time
etc. is computed directly from the track history).

### Evaluation metrics

- Segment-level precision/recall/F1 with prediction↔ground-truth matching = greedy
  highest-tIoU-first, one-to-one (no GT segment matched twice), requiring both
  `label match` AND `tIoU ≥ threshold`.
- tIoU thresholds swept at 0.3 / 0.5 / 0.7; average tIoU over matched pairs.
- Per-class precision/recall/F1 and a confusion matrix.
- Accuracy is explicitly **not** the headline metric — long background periods make
  it misleading; this is stated and justified in the report per the assignment's
  own instruction.
- **Eval-set-size caveat, stated explicitly in the report, not just implied:** with
  2-3 self-constructed videos (further split for validation vs. reporting),
  per-class precision/recall on rare classes will be noisy — single-digit support
  counts, not statistically stable estimates. The report states this plainly rather
  than presenting per-class numbers as more reliable than they are.

### `inference.py` / `evaluate.py` I/O contract

`inference.py --video <path> --output <path.json>` writes exactly the ground-truth
JSON schema (`{"video": ..., "segments": [{"start", "end", "label", "confidence"}]}`,
matching the schema shown in the Problem Statement), so `evaluate.py --predictions
<path.json> --ground-truth <gt.json>` composes directly against it with no
translation step. `evaluate.py` writes a JSON summary to
`outputs/metrics/<video>_metrics.json` (overall precision/recall/F1 at each tIoU
threshold, average tIoU, per-class precision/recall/F1, confusion matrix) and prints
a human-readable version of the same to stdout — no separate schema to design, it's
the same numbers in two forms.

## Feasibility risks (named upfront, not discovered mid-build)

- **CLIP zero-shot may land near chance on Theft/Chain-Snatching and Vandalism.**
  These classes often have a weak single-frame visual signature separating them
  from benign interactions (someone grabbing a bag looks like someone grabbing
  their own bag in a single frame). This is a real risk to the appearance branch,
  not just a hypothetical weakness — the report must measure and state this rather
  than assume prompt engineering fixes it.
- **Tracker fragility (ID switches, occlusion) directly corrupts dwell-time and
  owner-separation computations.** The rule engine's reliability is bounded by
  tracker quality; this is a dependency, not a detail, and gets called out in the
  failure-analysis section of the report if observed.
- Six rule-engine heuristics (zone occupancy, dwell time, velocity, density,
  bbox-shape, owner-separation) each need their own threshold, calibrated from only
  2-3 evaluation videos — this is a real time cost in the experiment phase, not a
  one-line config edit.
- The ≤2× real-time runtime budget is a target, not a measured guarantee — no
  per-frame YOLO/CLIP latency estimate backs it yet. First implementation pass
  measures actual throughput and the budget gets revised (or the mitigation levers
  tightened, e.g. lower detection fps) against real numbers, not the stated target.

## Success Criteria

- `python inference.py --video <any_new_video.mp4>` runs end-to-end with no code
  changes, on video never seen during development.
- Evaluation script computes tIoU-based precision/recall/F1 (and per-class
  breakdown) against a ground-truth JSON, with a documented matching strategy.
- At least one real qualitative timeline visualization (GT vs. prediction) is
  produced and saved to `outputs/visualizations/`, plus at least one frame/bbox+track
  overlay for the geometry branch (useful for debugging the tracker/rule engine and
  for demonstrating understanding of that branch specifically in an interview).
- Report states real, measured numbers only — any untested/unmeasurable class is
  named as a limitation, never assigned an invented metric.
- README explains exactly how to run inference on a new video and where output lands.

## Next Steps (implementation order)

1. `python3.12 -m venv .venv`, install deps (ultralytics/YOLO, CLIP via `open_clip`
   or `transformers`, opencv, numpy, pyyaml, pytest).
2. Source/construct 2–3 long evaluation videos + hand-authored ground truth JSON;
   author a zone config for any video that needs Intrusion/Running-in-zone coverage.
3. Geometry branch: YOLO11n + ByteTrack + rule engine, incl. abandoned-object
   owner-association logic (`src/rules/`).
4. Appearance branch: CLIP zero-shot windowed classifier with configurable
   multi-prompt-per-class scoring (`src/classifiers/`).
5. Temporal aggregation + segment builder placing both branches on one timeline,
   with same-class merge / cross-class overlap allowed (`src/pipeline/`).
6. Evaluation script (tIoU matching, precision/recall/F1, confusion matrix)
   (`scripts/evaluate.py`, `src/eval/metrics.py`).
7. Structured error analysis consuming the confusion matrix + per-class metrics
   (false-positive types, class confusions, temporal boundary error) — a distinct
   step, not folded silently into report writing.
8. Visualization: GT-vs-prediction timeline + geometry-branch bbox/track overlay
   (`src/eval/visualize.py`) → `outputs/visualizations/`.
9. `inference.py` CLI (`--video`, `--output`, `--threshold`, `--window-size`,
   `--stride`, `--device`, `--zones`), writing the shared prediction JSON schema.
10. Window/stride/threshold experiments on validation split → pick final config;
    document rule-engine threshold choices with the same rigor.
11. README + 2–4 page report with honest results, stated eval-set-size caveat,
    and failure analysis grounded in step 7's output.
